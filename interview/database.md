    A. 수평적 확장성(Scale-out)과 대규모 분산 데이터 처리 능력의 차이 때문입니다.

    확장
    트랜잭션(ACID)과 데이터 정합성이 필수이면서 일부 구조화되지 않은 데이터가 필요하다면 
    RDBMS의 JSON 타입이 적합합니다. 반면, 데이터의 유연한 구조와 
    막대한 쓰기 확장성이 우선이라면 NoSQL을 선택합니다.

    동일하거나 매우 유사한 해시 그룹을 묶고, 그 작은 그룹 내에서만 정밀 비교를 수행하여

<summary><strong>29. JPA N+1 문제 해결해서 수백번 나가던 쿼리를 단 1번에 처리하시오</strong></summary>

29. JPA N+1 문제 해결해서 수백번 나가던 쿼리를 단 1번에 처리하시오
    
    ```
    JPA N+1 문제는 연관 관계가 설정된 엔티티를 조회할 때, 
    1번의 쿼리로 N개의 데이터를 가져왔으나 연관 데이터를 조회하기 위해 
    N번의 추가 쿼리가 발생하는 성능 저하 현상입니다.
    
    A. JPQL의 `Fetch Join` 또는 Spring Data JPA의 `@EntityGraph`를 적용합니다.
    
    이유
    N+1 문제는 지연 로딩(Lazy) 설정된 연관 엔티티를 프록시 객체로 가져온 후, 
    실제 데이터에 접근하는 루프 과정에서 초기 1회의 쿼리 외에 N번의 SELECT 쿼리가 
    추가로 발생하는 현상입니다. 
    `JOIN FETCH` 구문을 사용하면 SQL 조인을 통해 연관된 데이터를 처음부터 포함하여 
    단일 쿼리로 모두 메모리에 적재하므로 지연 로딩 접근으로 인한 병목을 원천 차단합니다.
    
    확장
    - 컬렉션 조회 시 카테시안 곱(Cartesian Product)으로 인한 데이터 중복이 발생할 수 있으므로, 
      필요에 따라 `DISTINCT` 키워드를 함께 사용하여 영속성 컨텍스트 레벨에서 중복 엔티티를 필터링해야 합니다.
    - 컬렉션(`@OneToMany`)에 Fetch Join을 적용한 상태에서 페이징(`Pageable`) 처리를 시도하면, 
      하이버네이트는 DB 레벨의 페이징(Limit/Offset)을 포기하고 모든 데이터를 메모리에 적재한 뒤 
      애플리케이션 단에서 페이징을 시도하여 치명적인 OOM(Out of Memory) 장애를 유발합니다.
    - 따라서 `ToOne` 관계(`@ManyToOne`, `@OneToOne`)는 Fetch Join으로 페이징과 함께 한 번에 가져오고, 
      컬렉션은 지연 로딩을 유지하되 `hibernate.default_batch_fetch_size`(통상 100~1000)를 설정하여 
      지연 로딩 대상을 `IN` 쿼리로 묶어 N+1을 1+1 쿼리로 완화하는 하이브리드 전략이 프로덕션 표준입니다.
    ```

30. [복합 인덱스 컬럼 순서] 당신은 두 개의 인덱스를 가지고 있습니다: 인덱스 A: (user_id, created_at) / 인덱스 B: (created_at, user_id). 동일한 컬럼, 순서만 다릅니다. 쿼리: `WHERE user_id = 5 ORDER BY created_at DESC`. 어느 인덱스를 사용하시겠습니까? 왜입니까?
    
    ```
    인덱스 A, 왜냐하면 첫 번째 열은 정렬의 키로 사용되기 때문이며, 두 번째는 동점 해소에 사용됩니다.
    
    A. 인덱스 A `(user_id, created_at)`를 사용합니다.
    
    이유
    B-Tree 인덱스는 정의된 선행 컬럼부터 정렬이 적용됩니다. `WHERE` 절에서 동등(=) 조건으로 
    필터링하는 `user_id`가 선행 컬럼이고, 범위 검색 및 정렬(`ORDER BY`)에 사용되는 `created_at`이 
    후행 컬럼으로 구성된 인덱스 A를 사용해야만 데이터 필터링과 정렬 연산(Filesort) 생략을 동시에 
    처리할 수 있기 때문입니다.
    
    확장
    인덱스 B `(created_at, user_id)`를 타게 되면 전체 시간대별로 정렬된 상태에서 `user_id`를 
    찾아야 하므로, 인덱스의 검색 효율성이 극도로 떨어져 인덱스 풀 스캔이나 
    비효율적인 파일 정렬이 발생하게 됩니다. 
    (동등 조건은 앞쪽에, 범위/정렬 조건은 뒤쪽에 배치하는 것이 인덱스 설계의 기본 원칙입니다.)
    ```

<summary><strong>31. [글로벌 식별자 선택 전략] 두 명의 백엔드 엔지니어가 사용자 ID를 저장했습니다. 디자인 A : INT AUTO INCREMENT. 디자인 B : UUID. 이 앱은 전 세계적으로 확장될 것으로 예상됩니다. 어느 쪽을 선택하시겠어요?</strong></summary>

31. [글로벌 식별자 선택 전략] 두 명의 백엔드 엔지니어가 사용자 ID를 저장했습니다. 디자인 A : INT AUTO INCREMENT. 디자인 B : UUID. 이 앱은 전 세계적으로 확장될 것으로 예상됩니다. 어느 쪽을 선택하시겠어요?
    
    ```
    UUID는 조정 없이 전역적으로 고유하며, 순차적 누수가 없고, 샤딩이 깨지지 않습니다.
    
    A. 전 세계적인 글로벌 확장(Scale-out)을 고려하여 디자인 B(UUID)를 선택합니다.
    
    이유
    여러 국가와 리전에 걸쳐 데이터베이스가 샤딩(Sharding)되는 환경에서 INT AUTO INCREMENT를 사용하면 
    각 노드가 동일한 번호를 생성하여 충돌이 발생합니다. 반면 UUID는 중앙 서버의 발급 조율 없이도 
    로컬에서 충돌 확률이 0에 수렴하는 전역 고유 식별자를 즉시 생성할 수 있어 분산 시스템에 완벽히 적합하기 때문입니다.
    
    확장
    단, 순수 UUID v4는 무작위성 때문에 B-Tree 인덱스에 삽입될 때 디스크 단편화(Page Split)를 일으켜 
    성능이 크게 저하됩니다. 따라서 글로벌 확장이 필요하다면 시간 순 정렬이 가능한 UUID v7 이나 
    트위터의 Snowflake, ULID 같은 순차적 고유 식별자 방식을 채택하는 것이 현대적인 모범 사례입니다.
    ```

<summary><strong>32. [ORM의 N+1 병목] ORM에서 N+1 쿼리 문제를 어떻게 처리하나요?</strong></summary>

32. [ORM의 N+1 병목] ORM에서 N+1 쿼리 문제를 어떻게 처리하나요?
    
    ```
    N+1 쿼리 문제는 목록을 가져온 후 각 항목에 대해 관련 데이터를 로드하기 위해 추가 쿼리를 실행할 때 발생합니다.
    1. 초기 쿼리에서 관련 데이터를 가져오기 위해 즉시 로딩(Include()) 사용. 
    2. 필요한 필드만 가져오기 위해 프로젝션(Select()) 사용.
    3. 루프 내에서 쿼리하는 대신 일괄 로딩 사용.
    
    테이블들이 키(기본 키, 보조 키, 복합 키)로 적절하게 연결되어 있으면 Entity Framework Core와 같은 ORM은 효율적인 조인이나 
    최적화된 SQL을 생성할 수 있습니다. 그림 3에서 볼 수 있듯이, 불필요한 왕복 작업 없이 주문을 불러올 수 있었습니다.
    
    A. 즉시 로딩(Eager Loading) 적용, 필요한 필드만 가져오는 프로젝션(Projection), 
    그리고 일괄(Batch) 로딩 기법을 사용합니다.
    
    이유
    N+1 쿼리는 ORM이 기본적으로 연관 관계를 지연 로딩(Lazy Loading)으로 처리할 때 발생합니다. 
    부모 엔티티의 목록(1번 쿼리)을 가져온 후, 반복문을 돌며 연관된 자식 엔티티에 접근할 때마다 
    데이터베이스로 개별 쿼리(N번 쿼리)가 전송되어 심각한 네트워크 I/O 병목을 일으키기 때문입니다.
    
    확장
    외래 키(PK/FK) 제약 조건이 명확할 때 Entity Framework Core의 `Include()`, `Select()`나 
    JPA의 `Fetch Join` 등을 활용하면, ORM이 데이터베이스 레벨에서 최적화된 JOIN을 생성하거나 
    In-clause로 묶인 단일 쿼리를 발생시켜 불필요한 왕복 작업(Round-trip)을 근본적으로 제거할 수 있습니다.
    ```
