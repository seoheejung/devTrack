1. [중복 요청] `POST /api/orders` 엔드포인트가 있습니다. 네트워크 재시도로 인해 동일한 주문에 대해 여러 번 호출되고 있습니다. 사용자들이 두 번 청구되고 있습니다. 이것을 어떻게 수정하시겠습니까?
    
    ```
    A. idempotency를 보장하도록 API를 수정합니다.
    
    이유
    재시도 상황에서 동일 요청이 중복 처리되면 비즈니스 오류가 발생합니다.
    
    확장
    idempotency key, unique constraint, 요청 deduplication을 적용합니다.
    ```

<summary><strong>2. [GET vs POST] GET과 POST 요청의 차이점은 무엇인가요?</strong></summary>

2. [GET vs POST] GET과 POST 요청의 차이점은 무엇인가요?
    
    ```
    GET은 기본적으로 데이터를 가져오는 데 사용되고, 
    POST는 데이터를 보내는 데뿐만 아니라 응답을 받는 데도 사용됩니다.
    
    A. GET은 조회, POST는 상태 변경 요청입니다.
    
    이유
    GET은 idempotent하며 캐싱 가능, POST는 서버 상태를 변경합니다.
    
    확장
    GET은 URL 기반, POST는 body 기반 데이터 전달입니다.
    ```
    

</details>

<summary><strong>3. [413 vs 500 처리] 사용자가 50MB 파일을 보냄. 제한은 5MB입니다. API가 예외 발생: 500 </strong></summary>

3. [413 vs 500 처리] 사용자가 50MB 파일을 보냄. 제한은 5MB입니다. API가 예외 발생: 500   
백엔드 리드가 말함: "UI가 제한을 초과함. 그들이 고쳐야 함" 당신의 답변은?
    
    ```
    500은 백엔드가 요청을 처리하지 못했다는 의미입니다. 
    클라이언트가 아닌 백엔드 버그입니다. 
    API는 5MB 업로드 제한을 스스로 강제해야 하며, 명확한 오류와 함께 413을 반환해야 합니다. 
    UI 검사는 UX를 위한 것이지 강제 집행이 아닙니다(curl/postman은 이를 우회합니다). 
    또한 프론트엔드에서 더 나은 UX를 위해 업로드 전 크기 검사를 추가하세요. 
    하지만 500은 먼저 서버 측에서 수정해야 합니다.
    
    A. 서버에서 413 Payload Too Large를 반환하도록 수정해야 합니다.
    
    이유
    500은 서버 오류이며, 입력 검증 실패는 서버 책임입니다.
    
    확장
    프론트는 UX 개선용 검사, 서버는 반드시 강제 제한을 구현해야 합니다.
    ```

5. [GET + body] GET 요청에 본문(body)이 포함될 수 있나요? 프로덕션 환경에서 실제로 사용해 본 적이 있나요?

    확장

    복잡한 조건이면 POST를 사용하는 것이 일반적입니다.

<summary><strong>6. [비동기 작업의 HTTP 상태 코드] 사용자가 리소스를 삭제합니다. API는 200을 반환합니다. 하지만 삭제는 비동기적이며 아직 완료되지 않아 리소스가 잠시 나타날 수 있습니다. 이것은 좋은 설계인가요?</strong></summary>

6. [비동기 작업의 HTTP 상태 코드] 사용자가 리소스를 삭제합니다. API는 200을 반환합니다. 하지만 삭제는 비동기적이며 아직 완료되지 않아 리소스가 잠시 나타날 수 있습니다. 이것은 좋은 설계인가요?
    
    ```
    200을 반환하면 삭제가 완료된 것처럼 보이지만, 아직 완료되지 않았을 수 있습니다. 
    API에서 설명하는 내용과 실제 발생하는 상황 사이에 불일치가 발생합니다.
    
    A. 상태 코드 오용이며, `202 Accepted`를 반환해야 합니다.
    
    이유
    HTTP `200 OK`는 요청이 성공적으로 완료되었음을 의미합니다. 
    비동기 처리는 요청을 '수락'했으나 '처리 중'인 상태이므로 
    `202 Accepted`가 표준 규격에 부합합니다.
    
    확장
    `202` 반환 시 응답 헤더(`Location`)나 바디에 해당 작업의 상태를 
    폴링(Polling)할 수 있는 상태 확인 API 엔드포인트를 제공하는 것이 좋은 API 설계입니다.
    ```
    

</details>

<summary><strong>7. [프로토콜 선택 패러다임] WebSocket이 실시간 양방향 통신을 가능하게 한다면, 왜 모든 클라이언트-서버 통신에 WebSocket을 사용하는 대신 HTTP를 사용할까요?</strong></summary>

7. [프로토콜 선택 패러다임] WebSocket이 실시간 양방향 통신을 가능하게 한다면, 왜 모든 클라이언트-서버 통신에 WebSocket을 사용하는 대신 HTTP를 사용할까요?
    
    ```
    WebSocket은 지속적으로 열려 있는 연결을 유지합니다 (무겁고 확장하기 더 어렵습니다). 
    반면 HTTP는 가볍고, 캐시 친화적이며, 더 간단합니다.
    서버를 상태 유지(stateful)로 만들어 수평 확장 시 훨씬 더 많은 문제를 일으키며, 
    기본적인 CRUD 작업을 위해 WebSocket의 지속적인 연결을 만드는 것도 
    메모리를 과부하 상태로 만들 수 있습니다.
    
    A. HTTP가 더 가볍고, 상태 비저장(Stateless)이며, 캐시 및 확장에 유리하기 때문입니다.
    
    이유
    WebSocket은 연결을 지속적으로 유지해야 하는 상태 유지(Stateful) 특성 때문에 
    서버 메모리를 크게 소모하고 수평 확장(Scale-out)이 훨씬 까다롭습니다.
    
    확장
    단순한 데이터 조회(CRUD) 작업에는 캐시 친화적이고 비용이 저렴한 HTTP를 기본으로 사용하고, 
    채팅이나 주식 호가창처럼 실시간 양방향 데이터가 필수적인 도메인에만 
    제한적으로 WebSocket을 도입하는 것이 효율적입니다.
    ```
    

</details>

<summary><strong>8. [API 패러다임 트레이드오프] GraphQL이 유연성을 제공한다면, 왜 많은 회사들이 여전히 REST를 사용하는 걸까요?</strong></summary>

8. [API 패러다임 트레이드오프] GraphQL이 유연성을 제공한다면, 왜 많은 회사들이 여전히 REST를 사용하는 걸까요?
    
    ```
    GraphQL은 유연하지만 유연함에는 대가가 따른다
    많은 이들이 여전히 REST를 선택하는 이유:
    - 구축 및 디버깅이 더 간단함  
    - 쉬운 HTTP 캐싱 (CDN/브라우저)  
    - 복잡한 쿼리 남용 방지
    
    GraphQL은 복잡한 프론트엔드 데이터 요구사항에서 빛을 발한다.
    REST는 단순함 + 예측 가능성에서 승리한다
    
    A. REST가 아키텍처가 단순하고 캐싱과 예측 가능성 면에서 유리하기 때문입니다.
    
    이유
    GraphQL은 클라이언트에게 데이터 요청의 유연성을 주지만, 
    복잡한 쿼리 남용으로 인한 백엔드 부하(예: N+1 문제) 위험이 높고, 
    HTTP 레벨의 표준 캐싱(CDN 및 브라우저)을 활용하기 어렵기 때문입니다.
    
    확장
    프론트엔드의 데이터 요구사항이 매우 복잡한 서비스에서는 GraphQL이 강점을 가지나, 
    단순함, 명확한 디버깅, 안정적인 캐싱 및 예측 가능성이 중요한 대부분의 도메인에서는 
    REST가 여전히 승리합니다.
    ```
    

</details>

<summary><strong>9. [HTTP 상태 코드 정확성] 클라이언트가 잘못된 HTTP 메서드로 요청을 보냅니다. API가 405 대신 500을 반환합니다. 모든 것이 여전히 작동합니다. 이걸 버그로 간주하시겠습니까, 아니면 그냥 넘기시겠습니까?</strong></summary>

9. [HTTP 상태 코드 정확성] 클라이언트가 잘못된 HTTP 메서드로 요청을 보냅니다. API가 405 대신 500을 반환합니다. 모든 것이 여전히 작동합니다. 이걸 버그로 간주하시겠습니까, 아니면 그냥 넘기시겠습니까?
    
    ```
    이것은 버그입니다. 왜냐하면 500은 서버가 실패했음을 의미하지만, 
    여기서는 클라이언트가 잘못된 메서드를 보냈기 때문에 405여야 하거든요.
    심지어 동작이 정상적으로 되더라도, 이는 잘못된 상태 코드이고 계약을 깨뜨리며, 
    클라이언트를 혼란스럽게 하고 나중에 디버깅을 더 어렵게 만듭니다.
    
    A. 명백한 버그로 간주하고 `405 Method Not Allowed`로 수정해야 합니다.
    
    이유
    `500 Internal Server Error`는 백엔드 시스템의 실패를 의미하고, 
    `405`는 클라이언트의 잘못된 호출을 의미합니다. 
    상태 코드는 클라이언트와 서버 간의 '계약'이므로 이를 어기면 혼란을 초래하기 때문입니다.
    
    확장
    결과적으로 시스템이 안 터지고 동작한다고 해도, 향후 에러 로그 모니터링 시 
    실제 치명적인 서버 장애(500)와 단순 클라이언트 실수(405)를 구분할 수 없게 만들어 
    트러블슈팅 및 디버깅 비용을 크게 높입니다.
    ```

<summary><strong>10. [API 버전 관리 필요성] 테크 리드가 당신에게 말합니다: &quot;우리는 API 버전 관리가 필요 없어요. 그냥 엔드포인트를 업데이트하면 돼요.&quot; 동의하시겠어요?</strong></summary>

10. [API 버전 관리 필요성] 테크 리드가 당신에게 말합니다: "우리는 API 버전 관리가 필요 없어요. 그냥 엔드포인트를 업데이트하면 돼요." 동의하시겠어요?
    
    ```jsx
    API에 따라 다릅니다. 내부 앱에서만 사용되는 내부 API라면 괜찮지만, 
    내부 및 외부의 여러 애플리케이션과 연결된 API라면 버전 관리가 필요합니다. 
    여기서 핵심은 API를 누가 사용하는지, 모든 애플리케이션을 제어할 수 있는지 여부입니다.
    
    A. API의 사용 범위와 클라이언트 통제 가능 여부에 따라 다릅니다.
    
    이유
    프론트엔드와 백엔드가 강하게 결합되어 있어 동시에 배포 및 수정이 가능한 
    내부 단일 서비스라면 버전 관리가 오버헤드일 수 있습니다. 
    그러나 외부 고객사나 모바일 앱(강제 업데이트가 즉각적으로 불가능한 환경)이 
    사용하는 퍼블릭 API라면 기존 엔드포인트를 그냥 변경 시 하위 호환성(Backward Compatibility)을 깨뜨려 
    대규모 장애를 유발하기 때문입니다.
    
    확장
    제어할 수 없는 다수의 클라이언트가 존재하는 환경에서는 
    반드시 URL 경로(`/v1/users`), 요청 헤더, 또는 쿼리 파라미터 등을 통해 
    버전을 명시적으로 분리하여 기존 연동 시스템의 안정성을 보장해야 합니다.
    ```

<details>
<summary><strong>12. [타임스탬프 표준] &quot;타임스탬프는 항상 서버 로컬 시간으로 반환하세요.” 이거 괜찮으신가요?</strong></summary>

12. [타임스탬프 표준] "타임스탬프는 항상 서버 로컬 시간으로 반환하세요.” 이거 괜찮으신가요?
    
    ```
    A. 아니요, 글로벌 서비스 확장성과 데이터 통합을 위해 'UTC(ISO 8601)'를 사용해야 합니다.
    
    이유
    서버 로컬 시간은 서버 위치나 설정에 따라 변하며, 클라이언트가 여러 시간대의 데이터를 
    조합하거나 표시할 때 혼란과 계산 오류를 야기합니다.

    테이블 JOIN과 락 연산을 수행해야 합니다. 서버는 이 데이터를 JSON 문자열로 변환(직렬화)하느라 CPU를 소모하고, 
    클라이언트는 이를 다시 파싱하여 모바일 기기의 배터리와 메모리를 낭비하므로 
    시스템 전 구간에 걸쳐 병목이 누적됩니다.
    
    확장
    또한 내부 식별자, 타인의 연관 데이터 등 불필요한 메타데이터가 응답 객체에 과도하게 포함되어 전달되면, 
    의도치 않게 민감 정보가 브라우저에 노출되는 데이터 유출(Data Leak) 보안 리스크가 무의식적으로 증가합니다.
    ```

<summary><strong>21. [GraphQL의 버전 관리 철학] REST에서는 버전 관리가 더 쉬운 반면, GraphQL에서는 왜 피하기 더 어려운가요?</strong></summary>

21. [GraphQL의 버전 관리 철학] REST에서는 버전 관리가 더 쉬운 반면, GraphQL에서는 왜 피하기 더 어려운가요?
    
    ```java
    A. GraphQL은 단일 그래프 스키마를 공유하는 "버전 없는 API(Versionless API)"를 지향하여, 
    엔드포인트 분리가 불가능하기 때문입니다.
    
    이유
    REST는 URI(`v1/users`, `v2/users`) 수준에서 명확하게 구버전과 신버전의 아키텍처를 논리적으로 
    분리할 수 있습니다. 반면 GraphQL은 하나의 거대한 스키마 트리를 공유하므로, 기존 타입을 변경하거나 
    파괴(Breaking Change)하면 이를 참조하던 모든 구형 클라이언트의 쿼리가 즉시 실패하게 됩니다.
    
    확장
    이 때문에 GraphQL에서는 버전을 올리는 대신, 기존 필드에 `@deprecated` 지시어를 붙여 점진적인 
    퇴출(Deprecation)을 유도하며, 클라이언트의 필드 사용량(Telemetry)을 모니터링하여 완전히 
    사용되지 않음이 검증될 때까지 코드를 영구적으로 안고 가야 하는 유지보수 부담이 생깁니다.
    ```

<summary><strong>22. [HTTP 메서드 의미론과 뮤테이션] REST의 멱등성과 GraphQL의 뮤테이션 사이의 실제 차이점은 무엇인가요?</strong></summary>

22. [HTTP 메서드 의미론과 뮤테이션] REST의 멱등성과 GraphQL의 뮤테이션 사이의 실제 차이점은 무엇인가요?
    
    ```java
    A. REST는 HTTP 프로토콜 수준의 멱등성 규약(PUT, DELETE)을 준수하지만, 
    GraphQL의 뮤테이션은 단순한 POST 요청 내부의 개발자 정의 규약일 뿐입니다.
    
    이유
    REST에서 `PUT /orders/1`은 1번 호출하든 10번 호출하든 최종 서버 상태가 동일해야 함(멱등성)을 
    네트워크 표준으로 기대할 수 있어, 네트워크 장애 시 클라이언트가 안전하게 재시도할 수 있습니다. 
    반면 GraphQL은 모든 요청을 POST로 처리하며, `Mutation` 블록 안의 데이터 생성/수정/삭제 행위가 
    멱등하게 보장되는지는 전적으로 백엔드 개발자의 세부 로직 구현 여부에 달려있습니다.
    
    확장
    따라서 GraphQL Mutation을 설계할 때는 결제나 재고 차감 같은 민감한 API에 대해, 클라이언트가 
    자체적인 멱등 키(Idempotency Key)를 인자로 반드시 넘기도록 스키마에 강제하고 서버 측에서 
    중복 처리를 방어하는 로직을 명시적으로 설계해야 합니다.
    ```
