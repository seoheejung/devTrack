    대응은 문자열 결합이 아니라
    - prepared statement / parameter binding 사용
    - 허용된 필드와 연산자만 받는 whitelist 기반 파서 사용

5. [JWT vs Session 선택] JWT 대 세션 — 언제 무엇을 사용할까요?
    
    ```
    A. 서버 스케일 아웃과 무상태성이 중요하면 JWT, 
    보안 통제력과 즉각적인 세션 만료가 중요하면 Session을 사용합니다.
    
    이유
    Session은 서버에 상태를 저장하므로 강제 로그아웃이 쉽지만 
    분산 환경에서 세션 클러스터링 리소스가 듭니다. 
    JWT는 서버 부담을 줄여주지만 한 번 발급되면 탈취 시 만료 전까지 통제가 어렵습니다.
    
    확장
    마이크로서비스 환경이나 외부 API 인증은 JWT가 적합하며, 
    단일 모놀리식 구조나 높은 보안(금융 앱 등)이 요구되는 환경은 
    Session(또는 짧은 Access Token + 서버 관리 Refresh Token)이 적합합니다.
    ```

6. [캐시 관통(Cache Penetration) 방어] 해커가 데이터베이스에 존재하지 않는 ID를 요청하고 있습니다 (예: ID: -999). 이것은 Redis 캐시를 우회하여 DB에 직접 부하를 줍니다. 어떻게 막나요?
    
    ```
    캐시 미스가 데이터베이스 취약점으로 이어지는 것을 절대 용납해서는 안 됩니다.
    
    A. Null 캐싱(Sentinel) 또는 블룸 필터(Bloom Filter)를 적용합니다.
    
    왜 이렇게 판단했는지
    존재하지 않는 키에 대한 반복 요청으로 DB 리소스가 고갈되는 전형적인 
    '캐시 관통' 공격 패턴 기준.
    
    이유
    DB에 없는 데이터라도 짧은 TTL을 주어 Redis에 "데이터 없음" 상태로 캐싱하면, 
    해커의 후속 요청을 DB가 아닌 Redis 선에서 방어할 수 있습니다.
    
    확장
    - Null 캐싱: 제한된 유효하지 않은 요청 패턴 방어.
    - 블룸 필터: ID 공간이 방대하고 무작위 공격이 들어올 경우 앞단에서 효율적으로 차단.
    - Rate Limiting 병행: 클라이언트 IP/Token 기준의 스로틀링 추가 적용.
    ```

7. [JWT와 DB 저장] JWT는 DB에 저장되지 않습니다. 인터뷰에서 토큰이 DB에 저장된다고 말하는 걸 그만두세요!

<summary><h3>8. [네트워크 메타데이터 노출] HTTPS가 암호화되어 있다면 어떻게 ISP(인터넷 서비스 제공자)가 여전히 당신이 방문한 웹사이트를 알 수 있는 거죠?</h3></summary>

8. [네트워크 메타데이터 노출] HTTPS가 암호화되어 있다면 어떻게 ISP(인터넷 서비스 제공자)가 여전히 당신이 방문한 웹사이트를 알 수 있는 거죠?
    
    ```
    HTTPS는 콘텐츠를 숨기지만, 모든 메타데이터를 숨기는 것은 아닙니다. 
    (DNS 조회, 목적지 IP, SNI 등) 그들은 페이지를 읽을 수는 없지만, 
    종종 당신이 어디로 갔는지 유추할 수 있습니다.
    
    A. HTTPS는 페이로드(콘텐츠)를 암호화할 뿐, 
    네트워크 라우팅에 필요한 메타데이터까지 모두 암호화하지는 않기 때문입니다.
    
    이유

    TLS 핸드셰이크 과정에서 서버가 올바른 인증서를 제공할 수 있도록 
    평문 형태의 도메인 이름(SNI, Server Name Indication)을 전송합니다. 
    라우터와 ISP는 이 평문 데이터와 목적지 IP를 통해 
    사용자의 접속 목적지를 파악할 수 있습니다.
    
    확장
    이를 방지하기 위해 DNS over HTTPS(DoH)를 사용하여 DNS 조회를 암호화하고, 
    Encrypted Client Hello(ECH)를 통해 SNI까지 암호화하거나 
    전역적으로 VPN을 사용해야 합니다.
    ```

<summary><h3>9. [서버 측 웹 보안 취약점] 침투 테스트 문제. 다음 중 공격자가 서버를 통해 내부 포트를 무작위로 스캔할 수 있는 취약점은 무엇입니까? (A. SSRF / B. CSRF / C. XSS / D. IDOR)</h3></summary>

9. [서버 측 웹 보안 취약점] 침투 테스트 문제. 다음 중 공격자가 서버를 통해 내부 포트를 무작위로 스캔할 수 있는 취약점은 무엇입니까? (A. SSRF / B. CSRF / C. XSS / D. IDOR)
    
    ```
    A. SSRF (Server-Side Request Forgery, 서버 측 요청 위조)입니다.
    
    이유
    SSRF는 공격자가 서버를 속여, 
    서버 자신의 권한으로 악의적인 요청을 발생시키도록 만드는 취약점입니다. 
    공격자는 외부에서 접근할 수 없는 내부망(Intranet)이나 
    로컬 루프백(localhost)으로 서버가 직접 HTTP 요청을 보내게 조작하여, 
    방화벽 내부의 포트 개방 여부나 민감한 메타데이터(예: AWS EC2 IMDS)를 탈취할 수 있습니다.
    
    확장
    - CSRF (Cross-Site Request Forgery): 피해자의 브라우저 권한을 이용해 요청을 위조.
    - XSS (Cross-Site Scripting): 피해자의 브라우저에서 악성 자바스크립트를 실행.
    - IDOR (Insecure Direct Object Reference): 객체 참조에 대한 권한 검증 누락으로 
    타인의 데이터에 접근.
    ```

10. [401 vs 403 상태 코드] 로그인된 사용자, 관리자 기능 클릭. 관리자 자격 증명 입력 요청, 잘못된 관리자 자격 증명 입력. 무엇을 보내야 할까? 401인가 403인가?

    토큰 자체가 접근 증명입니다.
    
    A. "Bearer(소지자)"는 해당 토큰을 '소지(Bear)'하고 있는 클라이언트 누구에게나

    검사하여 접근을 허용(접근 증명)하기 때문에 상태 비저장(Stateless)과 서버 확장성에 매우 유리하기 때문입니다.

<summary><h3>31. [JWT 기반 인증의 도입 목적] 백엔드 개발자 여러분: 왜 API들은 세션 대신 JWT를 사용하는 걸까요?</h3></summary>

31. [JWT 기반 인증의 도입 목적] 백엔드 개발자 여러분: 왜 API들은 세션 대신 JWT를 사용하는 걸까요?
    
    ```
    API는 확장성이 필요하기 때문입니다.
    
    JWT는 상태 비저장(stateless)이므로, 어떤 서버든 세션 데이터를 조회하지 않고도 이를 검증할 수 있습니다. 
    이는 로드 밸런싱, 마이크로서비스, 그리고 수평적 확장을 훨씬 더 간단하게 만듭니다. 
    그 대가로, 취소(revocation)와 토큰 회전(token rotation)은 추가적인 설계가 필요합니다.
    
    A. 분산 서버 환경에서의 수평 확장성(Scale-out)을 쉽게 확보하고 로드 밸런싱의 복잡도를 낮추기 위해서입니다.
    
    이유
    세션(Session) 기반 인증은 사용자의 로그인 상태를 서버 메모리나 중앙 집중형 DB에 저장해야 하므로, 
    트래픽이 증가하여 서버 인스턴스를 늘릴 때마다 세션 정합성을 맞추는(Sticky Session 등) 인프라 비용이 
    크게 발생합니다. 반면 JWT는 서명과 인증 데이터가 토큰 자체에 포함된 무상태성(Stateless)을 가지므로, 
    어떤 서버 인스턴스든 토큰만 보고 즉각 검증이 가능해 확장이 극도로 자유롭기 때문입니다.
    
    확장
    마이크로서비스 아키텍처(MSA)에서는 각 서비스 간 권한을 전파할 때 JWT가 압도적으로 유리합니다. 
    그러나 서버가 상태를 관리하지 않는다는 것은, 한 번 발급된 토큰을 만료 시간 전까지 
    서버에서 강제로 무효화(Revocation)하기 어렵다는 보안적 트레이드오프(Trade-off)를 수반합니다.
    ```

32. [무상태 JWT의 강제 취소 전략] JWT는 상태 비저장(stateless)입니다. 그렇다면 손상된 JWT를 즉시 어떻게 취소하겠습니까?

    각 JWT에는 고유 키(JTI)가 포함되어 있으며, 이를 추출하여 Redis에 저장하고 만료 시간까지 Redis TTL을 추가하여

    A. Redis와 같은 인메모리 캐시를 활용하여 'JWT 블랙리스트(Blacklist)' 메커니즘을 구축해야 합니다.
    
    이유
    JWT는 자체적으로 유효성을 증명하므로, 로그아웃이나 비밀번호 변경과 같은 보안 이벤트 발생 시 
    서버가 이미 발급된 토큰을 능동적으로 폐기할 수 없습니다. 따라서 JWT에 포함된 고유 식별자(JTI - JWT ID)를 
    추출하여 Redis에 저장하고, 인가(Authorization) 필터 단계에서 해당 토큰이 블랙리스트에 존재하는지 
    교차 검증을 거쳐야만 강제 무효화가 가능해집니다.
    
    확장
    블랙리스트에 저장되는 JTI 데이터가 메모리에 무한히 쌓이는 것을 방지하기 위해, 
    Redis에 JTI를 저장할 때 남은 토큰의 유효 기간(만료 시간까지 남은 시간)을 TTL(Time-To-Live)로 설정합니다. 
    이를 통해 토큰이 자연 만료되는 시점에 블랙리스트 캐시에서도 자동 소멸되므로 메모리 효율을 극대화할 수 있습니다.
