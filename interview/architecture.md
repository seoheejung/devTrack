13. [Node.js 임계 처리량 문제] 당신의 Node.js 서버는 초당 100개의 요청을 잘 처리하지만, 초당 150개의 요청에서는 응답 시간이 50ms에서 5초로 급격히 증가합니다. 갑작스러운 성능 저하의 원인은 무엇일까요?
    
    ```
    Node.js는 단일 스레드 이벤트 루프에서 실행됩니다. 
    100 req/s에서 루프는 작업이 도착하는 것보다 빠르게 비워지지만, 
    150 req/s에서는 따라잡지 못하고 요청이 대기열에 쌓이기 시작합니다. 
    대기열에 쌓인 각 요청은 그 뒤의 모든 것에 지연을 추가하여 비선형적인 급증을 일으킵니다.
    
    A. 시스템이 임계 처리량을 넘어서 큐잉 지연이 폭증한 것입니다.
    
    왜 이렇게 판단했는지
    처리량 한계 초과 시 응답시간이 비선형적으로 급등하는 전형적 패턴 기준
    
    이유
    초당 100개까지는 서버가 감당 가능하지만
    150개부터는 처리 가능한 속도보다 유입 속도가 더 빨라져
    이벤트 루프, DB 커넥션 풀, 스레드풀, 내부 큐 중 하나에 대기가 쌓입니다.
    그 결과 평균 응답시간이 갑자기 수 초 단위로 튀게 됩니다.
    
    확장
    주요 원인 후보
    - DB connection pool 고갈
    - 외부 API/DB I/O 병목
    - event loop blocking
    - libuv thread pool 부족
    - GC pressure 증가
    - CPU saturation
    - 동시성 제한 지점(queue buildup)
    
    핵심은 "조금 느려진 것"이 아니라
    병목 자원의 처리 한계를 넘어서 대기열이 폭증한 상태라는 점입니다.
    ```

    ```java
    REST API는 `/users/123`처럼 리소스마다 고유한 URI를 가지며 HTTP 표준 의미론(GET)을 준수하므로 
    중간 네트워크 인프라가 URL을 식별자로 삼아 즉각적인 캐싱을 수행합니다. 그러나 GraphQL은 거의 모든 
    데이터 조회를 단일 `/graphql` 엔드포인트에 POST 메서드의 본문(Body)으로 보내기 때문에, 
    표준 HTTP 캐시 메커니즘을 전혀 활용할 수 없습니다.
    
    확장
    GraphQL에서 캐싱을 구현하려면 클라이언트 측(Apollo Client 등)에 정규화된 인메모리 캐시를 구축하거나, 
    서버 측에 Redis와 통합된 필드 단위의 객체 캐싱 로직을 직접 짜야 합니다. 또는 해시된 쿼리 아이디를 
    GET 파라미터로 넘기는 APQ(Automatic Persisted Queries) 기법을 도입해야 하는 등 
    캐싱 아키텍처 비용이 급증합니다.
    ```
